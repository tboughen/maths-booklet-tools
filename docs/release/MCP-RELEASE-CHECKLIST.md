# MCP routine release checklist

Use the [full playbook](MCP-RELEASE-PLAYBOOK.md) and
[shared pipeline](RELEASE-PIPELINE.md). This checklist does not grant publication.

1. Resolve current main, concurrent PRs and actual website/service/package/client
   identities. Preserve older worktrees. Identify authorisation scope.
2. Commit a stable candidate and compare the complete intended baseline. Derive
   impacts from actual paths; union mixed obligations and keep unknowns broad.
3. Create one fresh release record. Preflight intended-client access and record
   pending stages early. Retain old catalogue/source/artwork controls and an
   independently reviewed expected metadata delta.
4. Run focused local tests. Complete readiness and freeze explicit material files,
   binding candidate, policy, inputs and evidence. No mathematical/live pass is
   implied by the freeze.
5. Inspect an existing exact-head PR qualification before dispatching another.
   Use the bounded watcher. Require the entire sealed trusted aggregate, complete
   browser inventory and applicable full service/Linux/vector proof.
6. Independently verify retained artifacts and provenance. Browser slim fixtures
   must have their full manifest; service-only results need `qualified-service`.
   Source-only packages cannot be promoted as website packages.
7. Complete the five-pair compatibility matrix, including legacy files. Resolve
   incompatibilities and recovery limits before mutation.
8. Within authorised publication scope, use existing controlled website/manual
   service routes only when their surfaces changed. Check prior identity before
   mutation and actual build/schema/HTTPS/output identity afterward.
9. Prepare a three-way guarded package overlay; preserve concurrent edits, App
   binding/audience and stronger instructions. Re-read before upload; verify
   readback. No-op guidance does not need publication.
10. Perform the actual intended-client saved-resource journey through MathsDock,
    edit/save/MCP revision and exact file verification. Keep SDK, live service,
    client and human outcomes separate. Refresh metadata only when applicable.
11. Reconcile unknown/lost responses before retrying. Reuse verified stages only
    after current observation and saved-proof revalidation. Recheck frozen material
    before stage/decision commands; stop on newer independent state. Retain compatible
    previous source/packages/keys; report partial release honestly.
12. Report phase timings, waits, runner work, requests, failures and recovery.
    Keep unperformed client/Word/print/phone/teacher checks visible. Record next
    action and actual release stages. Done only after Tim confirms.
